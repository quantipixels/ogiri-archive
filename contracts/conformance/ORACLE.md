# DTA oracle observations and PROTOCOL rev 3.0 resolutions

The round-1 observations below were made against rev 2.1. The lead settled rev 3.0 separately; this suite does not edit the contract. These expectations come from the pinned, unpatched Rails 8.0.5.1 + DTA `b02076a930f7d0a4a155e25feaa7a50b86dbc625` + Devise `05811fb8366edd08874111d0f6fb44543e1c91ef` oracle. `test_http.py` names below reproduce the HTTP observations; the final run counts and commands are in the task report. Rails development API exception responses are empty 500 bodies in this configured reference.

## Source-only qualifications

`token_is_current?` also accepts `previous_token` until the session expires, without consulting batch age (user.rb lines 118-138); only the older `last_token` fallback checks the batch buffer. The rotation suite proves the older-token batch/rejection case, but does not separately claim a live proof of this immediate-previous-token edge.

The H1/H3 long-client request uses an unknown 65-character client. It proves rejection of that request; it does not establish a separate DTA length guard for an artificially seeded valid overlength client. The Ogiri schema limits stored clients to 64 characters.

S2's unknown-email timing equivalence is not measured. DTA's explicit dummy password hash is conditional on paranoid mode (sessions_controller.rb). HTTP assertions cannot prove lookup constant time or CSPRNG strength.

T2's independent-connection checks establish visibility and database-clock plausibility, not the surrounding-application-transaction/startup-DDL guarantees. Those need implementation or instrumented checks.

## Intentional exclusions and corrected hypotheses (round 1)

D-R, D-Q and D-S are explicitly marked Ogiri-only and skipped with reasons against the reference. Added D1-D3 device routes and T2 separate-store checks are also reference skips. O1 is a documented OAuth skip; no fake provider is supplied. These exclusions must not be mistaken for passed DTA behavior.

The initial suspicion that P3 stores the raw reset token was disproved: the database digest remains distinct from the emailed raw token after following the link. `test_E1_email_tokens_and_config` checks that, and strict proves raw confirmation storage versus digested unlock storage.

AC2 uses two real Rails processes sharing PostgreSQL. Cross-language AC2 remains for the library builders. AC3 uses published vanilla-token-auth 1.0.6; current active maintenance could not be established, as documented in README. No JS auth method is mocked.

## Rev-3 proof boundary and open questions

`ogiri_only` cases skip under `--reference` with their §13 difference id. `reference_only` cases skip on Ogiri; the suite never requires Ogiri to reproduce a native Rails crash or storage bug. Shared behavior includes sliding rotation, literal one-space batch headers, paranoid S3/S4, default false password checks, and missing-redirect-first P2 precedence. S6/R10 and Ogiri D2-current/D3 assert the complete absence of auth response headers after revocation.

D-R remains a configured-default probe unless the sample is launched without its rotation variable. D-P (unsupported Devise pepper) has no HTTP setting in the sample interface and requires implementation/configuration review. D-M has live-check code for legacy raw confirmation rejection; legacy secret-derived reset/unlock migration rejection is not separately proven. New E1 SHA-256 storage and peer redemption are checked for all three link kinds on Ogiri. These Ogiri cases are **not proved by a green reference run**.

Contract questions (PROTOCOL remains untouched):

- Valid C1/R11 with no request/default redirect: which status/body, and must the confirmation mutation persist? Recommendation: specify 404 with a defined body after successful confirmation, avoiding invented redirects.
- C1 allowlist: should the link endpoint enforce it, and what exact rejection body/status? Recommendation: use P3's 422 shape and reject before confirming.
- R6 says supplied current_password is otherwise ignored, but DTA checks it even under default false and §13 names only P4/P5. The suite follows literal R6 on Ogiri. Recommendation: explicitly list R6 under D-B, or adopt DTA and change R6.
- T5 refers to D3 retaining the most recent client, while D3 revokes every client. Suite follows D3 revoke-all. Recommendation: remove D3 from T5's recency sentence; recency applies to P6.
- H2/K1 does not specify cookie-versus-Bearer order, or whether unchanged cookie writes may be suppressed. Recommendation: state cookie precedence and allow unchanged-cookie suppression explicitly if adopting the reference.
- D-K specifies the CSRF requirement but no rejection status/body. The Ogiri check requires a 4xx without revocation and checks successful matching-token sign-out; settle the exact error shape before tightening it.
